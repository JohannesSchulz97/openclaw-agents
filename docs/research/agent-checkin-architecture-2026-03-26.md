# Agent Check-in Architecture Analysis

**Date:** 2026-03-26
**Scope:** Cron jobs, polling, check-in flow, agent tools, memory/state

---

## 1. Executive Summary

The openclaw-agents system runs autonomous AI agents (called "Kais") on the OpenClaw platform. Each agent is a Developer Personal Assistant (type: `dev-pa`) assigned to a specific developer. The check-in system uses a **cron-triggered polling mechanism** that determines whether the agent should proactively message its developer on Slack, based on time since last human interaction.

**Key flow:** Cron fires every 2 hours -> Agent runs `poll-check.sh` -> Script checks session timestamps -> If 4+ hours since last human interaction, agent composes a personalized Slack message -> Agent updates state to `awaiting_response: true`.

### Job Properties (identical across all agents)

- **sessionTarget:** `isolated` (does not pollute the main conversation session)
- **wakeMode:** `now` (immediate execution)
- **payload.kind:** `agentTurn` (agent receives a message and responds)
- **payload.timeoutSeconds:** 120 (2 minute timeout per execution)
- **payload.thinking:** `on` (extended thinking enabled)
- **delivery.mode:** `none` (no automatic delivery to channels; agent sends manually)
- **sessionKey:** `agent:<name>:main` (scoped session key)

### Cron Application Process

`scripts/apply-cron.sh` reads `jobs-config.json` and syncs to the OpenClaw gateway:
- Matches jobs by `agentId` (not by config `id`, which is informational only)
- Uses `openclaw cron edit` for existing jobs, `openclaw cron add` for new ones
- Converts `everyMs` to human-readable duration (e.g., 7200000ms -> "120m")
- Applies all fields: name, agent, enabled/disabled, schedule, session, wake mode, message, model, thinking, timeout, session-key, delivery mode

## 3. Check-in Flow (End-to-End)

### Step-by-step sequence:

```
1. CRON TRIGGER (every 2 hours)
   |
   v
2. OpenClaw starts ISOLATED session for agent
   - Uses model: fw-mm25
   - Thinking: on
   - Timeout: 120 seconds
   |
   v
3. Agent receives PAYLOAD MESSAGE instructing it to:
   "Run scripts/poll-check.sh. Parse the JSON output."
   |
   v
4. Agent executes poll-check.sh
   |
   v
5. poll-check.sh performs DECISION LOGIC:
   a. Reads poll-config.json (interval_minutes, default: 240)
   b. Reads memory/poll-state.json (awaiting_response flag)
   c. Reads sessions.json (finds last non-cron session timestamp)
   d. Calculates elapsed minutes since last human interaction
   e. Returns JSON: { due: 0|1, interval_minutes, elapsed_minutes,
                       awaiting_response, last_human_interaction, agent_name }
   |
   v
6. Agent parses JSON response:
   |
   +-- If data.due == 0 --> Output "NO_ACTION" and session ends
   |
   +-- If data.due == 1 --> Proceed to check-in:
       |
       v
7. Agent reviews conversation history and memory files
   (SOUL.md, USER.md, memory/YYYY-MM-DD.md, MEMORY.md)
   |
   v
8. Agent composes personalized check-in message
   - Must be warm, friendly, specific
   - Must reference something developer was working on
   - Must avoid generic phrases like "just checking in"
   |
   v
9. Agent sends message via:
   openclaw message send --channel slack --target user:<SLACK_ID> --message "<message>"
   |
   v
10. Agent updates memory/poll-state.json:
    { "awaiting_response": true }
```

### Decision Logic Detail (poll-check.sh)

The script implements three branches:

1. **`awaiting_response == true`**: Always returns `due: 0`. The agent already sent a check-in and is waiting for the developer to reply. No new check-in should be sent. (Note: the `awaiting_response` flag must be reset by some other mechanism when the developer responds.)

2. **No human sessions found** (`LAST_HUMAN_EPOCH_S` is empty): Returns `due: 1`. This handles fresh agents that have never had a human interaction.

3. **Normal case**: Calculates `elapsed_minutes = (now - last_human_epoch) / 60`. If `elapsed_minutes >= interval_minutes` (default 240), returns `due: 1`. Otherwise returns `due: 0`.

### Session Timestamp Source

The script reads `~/.openclaw/agents/<agent-name>/sessions/sessions.json`:
- Filters OUT sessions whose key contains "cron" (to avoid counting cron wakeups as human interaction)
- Takes the MAX `updatedAt` timestamp from remaining sessions
- This ensures only genuine human-initiated conversations count toward the "last interaction" timer

## 4. Data Available Before Check-in

When the agent wakes up for a cron check-in, it has access to:

### Always Available (Agent Workspace)
- **SOUL.md** - Agent personality, core values, behavior guidelines
- **IDENTITY.md** - Agent's name, creature type, vibe, emoji (filled during bootstrap)
- **USER.md** - Developer's name, timezone, preferences, project context
- **AGENTS.md** - Operating manual (session startup protocol, memory management, red lines)
- **TOOLS.md** - Environment-specific tool notes (currently a template)
- **HEARTBEAT.md** - Periodic task checklist (currently a template)

### Memory Files
- **memory/YYYY-MM-DD.md** - Daily notes with raw logs of interactions
- **memory/poll-state.json** - Check-in state (`awaiting_response` flag)
- **MEMORY.md** - Curated long-term memories (if exists)

### Session Context
- The cron job uses `sessionKey: "agent:<name>:main"`, giving it access to the agent's main session conversation history
- The agent can review recent conversation history to understand what the developer has been working on

### poll-check.sh Output
- `due` (0 or 1) - whether check-in is needed
- `interval_minutes` - configured interval (default 240)
- `elapsed_minutes` - time since last human interaction
- `awaiting_response` - current state flag
- `last_human_interaction` - ISO timestamp of last interaction
- `agent_name` - the agent's name

## 5. How the Agent Decides What to Say

The cron payload message provides explicit instructions:

1. **Review conversation history and memory** - The agent reads its memory files and recent conversations to understand what the developer has been working on
2. **Compose a personalized message** with these constraints:
   - Must be "warm, friendly"
   - Must be "specific" -- reference something the developer was working on or mentioned recently
   - Goal is to be "supportive and helpful, not generic"
   - Must avoid canned phrases like "just checking in"
   - Should "ask a thoughtful question or offer help with something concrete"
3. **The agent has thinking mode ON** (`thinking: "on"`) -- this enables extended reasoning before composing the message

The agent's personality (from SOUL.md) also shapes the message:
- "Be genuinely helpful, not performatively helpful"
- "Have opinions"
- "Be resourceful before asking"
- Concise when needed, thorough when it matters

## 7. Timing Summary

| Parameter | Value | Notes |
|-----------|-------|-------|
| Cron fire interval | Every 2 hours (7200000ms = 120 min) | How often the cron job runs |
| Check-in threshold | 240 minutes (4 hours) | How long since last human interaction before check-in triggers |
| Session timeout | 120 seconds | Max time for agent to complete the check-in task |
| Quiet hours | 23:00-08:00 | Mentioned in AGENTS.md (for heartbeats) but NOT enforced in poll-check.sh |

### Timing Analysis

- The cron fires **every 2 hours** but the check-in only triggers when the developer has been inactive for **4+ hours**
- This means: After a developer stops interacting, the **first check-in arrives between 4-6 hours later** (4 hours of inactivity + up to 2 hours until the next cron fires)
- Once `awaiting_response: true` is set, **no further check-ins are sent** until the flag is cleared
- The `awaiting_response` flag reset mechanism is NOT visible in the cron job -- it likely gets reset when the developer sends a message in the main session (or manually)

### Gap: Quiet Hours Not Enforced

AGENTS.md mentions "Late night (23:00-08:00) unless urgent" as a time to stay quiet, but `poll-check.sh` does NOT implement any time-of-day filtering. The agent could potentially check in at 3 AM if the 4-hour threshold is met.

## 9. Architecture Observations

### Strengths
1. **Clean separation**: Cron fires -> script checks -> agent decides. The script is deterministic, the agent adds intelligence.
2. **Isolated sessions**: Cron sessions don't pollute main conversation history.
3. **Shared type system**: All `dev-pa` agents share the same scripts and operating manual via `types/dev-pa/` + `sync-agents.sh`.
4. **State is minimal**: Only one flag (`awaiting_response`) + one config value (`interval_minutes`) drive the logic.
5. **JSON response library**: `lib/json-response.sh` provides standardized success/error output format.

### Potential Issues
1. **No quiet hours enforcement** in `poll-check.sh` -- agents can message developers at night.
2. **`awaiting_response` reset mechanism is unclear** -- how/when does it get set back to `false`?
3. **No per-agent schedule customization** in the cron config -- all agents fire on the same 2-hour cycle.
4. **No heartbeat-state.json** exists for any agent, despite AGENTS.md documenting it -- suggests heartbeat-based checks (email, calendar, weather) are not yet implemented.
5. **TOOLS.md is a bare template** for all agents -- no environment-specific tools configured yet.
6. **HEARTBEAT.md is a bare template** -- no periodic tasks configured beyond the cron check-in.
